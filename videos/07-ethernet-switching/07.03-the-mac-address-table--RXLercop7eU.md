## Цель для обучающегося

Обучающийся должен понять, что при отправке пакета в другую сеть Ethernet-кадр адресуется **MAC-адресу шлюза по умолчанию** (маршрутизатора), а не удалённого узла; что коммутаторы при этом работают как обычно — известный источник лишь обновляет пятиминутный таймер записи, неизвестное назначение затапливается, — и что обратный кадр от маршрутизатора (с IP-источником удалённого узла, но MAC-источником маршрутизатора) заставляет оба коммутатора выучить 00-0D и уйти к PC-A точечно.

Текст 7.3.5 — три фразы плюс примечание об IP-адресах в пакете. Видео добавляет всю механику: (1) кадр с `Data: Destination IP address on a remote network` и Dst MAC 00-0D; (2) поведение «источник известен → обновить таймер» (в тексте 7.3.3 это есть для одного коммутатора); (3) фильтрацию на PC-B и PC-C и приём на маршрутизаторе; (4) обратный кадр с `Data: Source IP address on a remote network`, запись `4 00-0D` в S2 и S1; (5) итоговые таблицы с несколькими MAC-адресами за одним межкоммутаторным портом (S1 порт 4: 00-0D; и если бы были ещё узлы за S2 — все они).

## Сценарий

Схема та же, что в 7.3.4: **S1** (порт 1 — PC A `00-0A`, порт 3 — PC B `00-0B`, порт 4 ↔ S2 порт 1), **S2** (порт 3 — PC C `00-0C`, порт 4 — Router порт 1 `MAC 00-0D`), Router порт 2 → **Internet**. Начальные таблицы: S1 — `1 00-0A`, `3 00-0B`; S2 — `1 00-0A`. Полоса кадра внизу: `Destination MAC | Source MAC | Type | Data | FCS`, где поле Data подписано текстом.

## Предложение по пересборке

**Формат:** `анимация Figma (≤ 60 с)` на том же ассете-схеме, что 7.3.4, продолжение с итоговых таблиц; при озвученной версии — `видео с генерированным голосом (код-рендер)` ~1:45, или объединить 7.3.4 + 7.3.5 в один ролик ≈ 3:30 «Два коммутатора: три кадра». Симулятору CLI не требуется; примечание из текста 7.3.5 про IP-адреса стоит визуализировать прямо в поле Data кадра (как в оригинале).

Сцены для генератора:

1. **Старт** → схема с таблицами S1 `1 00-0A, 3 00-0B`, S2 `1 00-0A`; кадр `Dst 00-0D / Src 00-0A / Data: IP назначения в удалённой сети` → «Пакет в другую сеть — кадр адресован шлюзу по умолчанию, MAC 00-0D.»
2. **S1: таймер + flooding** → мигание строки `1 00-0A`, стрелки из портов 2, 3, 4; ✗ у PC-B → «Источник известен — обновили таймер; 00-0D неизвестен — затопили.»
3. **S2: таймер + flooding** → мигание `1 00-0A`, стрелки 2, 3, 4; ✗ у PC-C; ✓ у Router → «Маршрутизатор узнаёт свой MAC и принимает кадр.»
4. **Ответ** → кадр `Dst 00-0A / Src 00-0D / Data: IP источника в удалённой сети` → «Обратно: MAC источника — маршрутизатора, IP источника — удалённого узла.»
5. **S2 учится** → строка `4 00-0D` в S2; стрелка в порт 1 → «S2 записывает 00-0D за портом 4 и шлёт точечно.»
6. **S1 учится** → строка `4 00-0D` в S1; одна стрелка в порт 1; ✓ у PC-A → «S1 записывает 00-0D за портом 4 и отдаёт кадр только PC-A.»
7. **Итог** → таблицы крупно; подсветка: за портом 4 S1 — MAC маршрутизатора (и всех узлов за S2) → «За одним портом может быть много MAC-адресов.»

Ассеты: те же, что в 7.3.4 (схема, таблицы, полоса кадра с текстовым полем Data, стрелки, ✓/✗); дополнительная подпись «таймер 5 мин».

**Замечания к оригиналу:** фактических ошибок нет. Ролик не поясняет, откуда PC-A знает MAC шлюза (ARP — модуль 9) — при пересборке добавить одну фразу-ссылку. На титуле обещаны два вопроса, но ролик также показывает третий случай — «источник известен → обновить таймер» — стоит вынести в титул.
