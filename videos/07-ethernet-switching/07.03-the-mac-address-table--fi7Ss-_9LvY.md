## Цель для обучающегося

После просмотра обучающийся должен уметь проследить, как **каждый** коммутатор на пути кадра независимо выполняет два шага (изучить MAC источника → найти MAC назначения), объяснить, почему первый кадр затапливается на обоих коммутаторах, а ответ уже уходит только в один порт S1, и почему S2 этот ответ не видит и MAC 00-0B не узнаёт; понимать, что у одного порта (S1 порт 4 / S2 порт 1) в таблице может оказаться несколько MAC-адресов — ровно то, о чём говорит текст 7.3.4.

Текст 7.3.1–7.3.3 описывает двухшаговый процесс для одного коммутатора (PC-A → PC-D, таймер 5 минут, фильтрация). Видео добавляет: (1) цепочку из двух коммутаторов — таблицы заполняются независимо и асимметрично; (2) поведение конечных узлов — PC-C и маршрутизатор сравнивают MAC назначения со своим и отбрасывают кадр; (3) что известный unicast от PC-B к PC-A не покидает S1. Это также схема-основа для 7.3.5.

## Сценарий

Схема неизменна на всём протяжении ролика (меняются только подсветка портов, стрелки, галочки/крестики и строки таблиц):

* **S1** — 4 порта: 1 → PC **A** (`MAC 00-0A`), 3 → PC **B** (`MAC 00-0B`), 4 ↔ S2 порт 1; порт 2 свободен.
* **S2** — 4 порта: 1 ↔ S1 порт 4, 3 → PC **C** (`MAC 00-0C`), 4 → **Router** порт 1 (`MAC 00-0D`); порт 2 свободен. Router порт 2 → облако **Internet**.
* Над коммутаторами — «S1 MAC Address Table» и «S2 MAC Address Table» (`Port | MAC Address`), вначале пустые.
* Внизу — полоса кадра Ethernet: `Destination MAC` (зелёный) | `Source MAC` (красный) | `Type` | `Data` | `FCS`.

## Предложение по пересборке

**Формат:** `анимация Figma (≤ 60 с)` без голоса как замена/дополнение иллюстраций 7.3.3 **плюс** (опционально) `видео с генерированным голосом (код-рендер)` ~2:00 с тем же сценарием. Содержание целиком укладывается в одну неизменную схему с подсветками. Делать одну схему-ассет на два ролика (7.3.4 и 7.3.5) — второй продолжает с итогового состояния таблиц этого.

Сцены для генератора:

1. **Титул** → «Таблицы MAC-адресов на двух коммутаторах» → «PC-A отправит кадр PC-B, затем PC-B ответит.»
2. **Схема + кадр A→B** → схема, пустые таблицы, кадр `Dst 00-0B / Src 00-0A` → «MAC источника 00-0A, назначения 00-0B.»
3. **S1 учится** → подсветка порта 1 S1, строка `1 | 00-0A` → «S1 не знает 00-0A — записывает его за портом 1.»
4. **S1 затапливает** → стрелки из портов 2, 3, 4; ✓ у PC-B → «00-0B в таблице нет — кадр во все порты, кроме входящего. PC-B узнаёт свой MAC.»
5. **S2 учится и затапливает** → строка `1 | 00-0A` в S2; стрелки из портов 2, 3, 4; ✗ у PC-C и Router → «S2 тоже записывает 00-0A за портом 1 и тоже затапливает; чужие отбрасывают.»
6. **Кадр B→A** → кадр `Dst 00-0A / Src 00-0B`; порт 3 S1; строка `3 | 00-0B` → «PC-B отвечает. S1 записывает 00-0B за портом 3.»
7. **Известный unicast** → одна стрелка из порта 1 S1 к PC-A, ✓ → «00-0A уже в таблице — только порт 1. S2 этот кадр не видит.»
8. **Итог** → таблицы крупно: S1 `1 00-0A`, `3 00-0B`; S2 `1 00-0A` → «Каждый коммутатор учится только по кадрам, которые через него проходят.»

Ассеты: схема (S1, S2 по 4 порта; PC A/B/C с MAC; Router с 2 портами, MAC 00-0D; облако Internet); два блока-таблицы `Port | MAC`; полоса кадра с заменяемыми значениями; стрелка, ✓, ✗.

Для симулятора CLI не требуется; естественное дополнение — лаборатория 7.3.7 (`show mac address-table` на S1/S2 после пинга PC-A → PC-B: на S2 будет только запись для PC-A).

**Замечания к оригиналу:** фактических ошибок нет; в авто-субтитрах MAC PC-B один раз расшифрован как «c000b» — это 00-0B. На схеме порт 2 обоих коммутаторов пуст, но стрелка затопления из него рисуется — верно (flooding во все порты, кроме входящего).
