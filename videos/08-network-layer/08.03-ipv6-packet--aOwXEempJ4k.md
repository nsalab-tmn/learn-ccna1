## Цель для обучающегося

Обучающийся должен уметь читать ветку «Internet Protocol Version 6» в Wireshark и сопоставлять её поля с IPv4: Version 6 (`0110 ....`), Traffic class ≈ DS, Flow label (новое), Payload length ≈ Total Length, Next header ≈ Protocol (6 = TCP, 58 = ICMPv6), Hop limit ≈ TTL (64 у хоста, 255 у NDP), Source/Destination; отличать глобальный unicast (`2001:…`) от link-local (`fe80::…`) и multicast (`ff02::…`) адресов, узнавать EUI-64 по `ff:fe` в середине идентификатора интерфейса и понимать, что Neighbor Solicitation — аналог ARP-запроса.

Текст 8.3.1–8.3.4 описывает поля и заголовки расширений. Видео добавляет: (1) вид полей в Wireshark, включая битовую запись `0110 .... = Version: 6`; (2) реальные значения Payload length 40 / 260 / 32, Next header 6 / 58, Hop limit 64 / 255; (3) три типа адресов на практике; (4) первое знакомство с ICMPv6 ND (Neighbor Solicitation, solicited-node multicast `ff02::1:ffxx:xxxx`), которое текст откладывает до модулей 9 и 12. Заголовков расширений в примерах нет.

## Предложение по пересборке

**Формат:** `видео с генерированным голосом (код-рендер)` ~3:00 — рендер дерева диссектора, как для 8.2.3, с **параллельной колонкой IPv4 ↔ IPv6** (Traffic class ↔ DS, Payload length ↔ Total Length, Next header ↔ Protocol, Hop limit ↔ TTL); три пакета — SYN / GET / NS. Данные — из современного захвата с документационными адресами (`2001:db8:…`). Для симулятора — те же три пакета как эталон просмотрщика; CLI не нужна.

Сцены для генератора:

1. **Пакет 46** → список + ветка IPv6; подсветка `2001:…` у Src/Dst → «Глобальные unicast-адреса; соединение TCP с веб-сервером.»
2. **Поля** → по одному: `0110 … = Version: 6`, `Traffic class`, `Flowlabel`, `Payload length: 40`, `Next header: TCP (6)`, `Hop limit: 64`, Source, Destination; рядом колонка «в IPv4 это…» → по фразе на поле.
3. **Пакет 49 (GET)** → `Payload length: 260`, под IPv6 — TCP, HTTP → «Та же оболочка, больше груза.»
4. **Пакет NS** → Src `fe80::211:25ff:fe82:95b5` (подсветка `ff:fe` → EUI-64), Dst `ff02::1:ff82:95b5` (solicited-node multicast), Ethernet Dst `33:33:ff:82:95:b5` → «Link-local → multicast; это аналог ARP: ищем MAC соседа.»
5. **Поля NS** → `Payload length: 32`, `Next header: ICMPv6 (58)`, `Hop limit: 255` → «255 — NDP-пакеты не должны проходить через маршрутизатор.»
6. **Карточка** → таблица соответствий IPv4 ↔ IPv6 и три пакета (94/314/86 байт; payload 40/260/32; next header 6/6/58; hop limit 64/64/255) → итог.

Ассеты: рендер окна анализатора; колонка соответствий; карточка сравнения; подсветка частей IPv6-адреса (префикс / `ff:fe` / solicited-node).

**Замечания к оригиналу (исправить при пересборке):**
1. **Payload length ≠ «общий размер пакета»**: это длина полезной нагрузки *без* 40-байтного заголовка IPv6 (в кадре 46 — 40 байт TCP-заголовка с опциями; весь IPv6-пакет — 80 байт). Total Length в IPv4, наоборот, включает заголовок. Диктор дважды говорит «total size of the packet».
2. **Neighbor Solicitation ищет не «link-local адрес», а MAC-адрес** (link-layer address) уже известного IPv6-адреса — как ARP. Фраза «hoping to get back a link local address» неверна.
3. **«NS для того же устройства, с которым общались раньше»** — не подтверждается: NS отправляет хост `Ibm_82:95:b5` (который в первом захвате был Ethernet-*назначением* — вероятно, шлюз), а solicited-node адрес `ff02::1:ff82:95b5` соответствует адресу с теми же последними 24 битами, что у самого отправителя; цель NS на экране не видна. Три NS с интервалом 1 с — стандартные повторы разрешения адреса. При пересборке взять однозначный пример: хост → NS → сосед отвечает Neighbor Advertisement.
4. `ff02::1:ffxx:xxxx` стоит назвать «solicited-node multicast», а не просто «multicast».
5. Описание Flow label («держать поток на одном пути через маршрутизаторы и коммутаторы») — упрощение; в тексте 8.3.3 точнее.
6. Адреса реальные (`2001:6f8::/32` — провайдерский префикс) — заменить на `2001:db8::/32`.
