## Цель для обучающегося

Обучающийся должен научиться находить в Wireshark ветку IPv4 в панели деталей пакета и читать её поля на реальных пакетах: Version 4, Header length 20 bytes, DSCP, Total Length, Identification, Flags (DF), Fragment offset, TTL 128, Protocol (6 = TCP, 1 = ICMP), Header checksum, Source/Destination; видеть, что в одном сеансе эти поля почти не меняются, а различаются Total Length (52 / 411 / 60), Identification, Flags и Protocol — и что под IPv4 лежит заголовок следующего уровня (TCP, затем HTTP; ICMP).

Текст 8.2.1–8.2.2 описывает поля абстрактно (с рисунком заголовка). Видео добавляет: (1) как эти поля выглядят в Wireshark (трёхпанельное окно: список пакетов, детали, байты); (2) значения полей для трёх типов пакетов — SYN без данных, GET с данными, ICMP; (3) связь Protocol → следующий раскрываемый заголовок (TCP / ICMP) и Total Length с размером кадра (66 / 425 / 74 байт на проводе); (4) практическую роль TTL (traceroute/ping) и DF. Ничего не говорит о фрагментации по MTU и об Options/Padding — как и текст.

## Предложение по пересборке

**Формат:** `видео с генерированным голосом (код-рендер)` ~3:00 — не скриншоты старого Wireshark 1.8, а рендер «дерева диссектора» (список пакетов + раскрытая ветка IPv4) с подсветкой поля в момент его упоминания и всплывающей подписью смысла; три пакета — как в оригинале (SYN / GET / ICMP), чтобы показать, что меняется. Данные для рендера брать из современного захвата (или из `.pcap`, собранного в лаборатории курса), сохранив те же адреса. Для симулятора: если в тренажёре есть просмотрщик пакетов (как PDU Details в PT), использовать те же три пакета как эталон; CLI-сессия не нужна.

Сцены для генератора:

1. **Три панели** → окно: список (пакеты 1–8), детали, байты; подсветка ветки `Internet Protocol Version 4` → «Сетевой уровень — вот эта ветка.»
2. **Пакет 2, адреса** → `Src 192.168.1.109 → Dst 192.168.1.1`, в списке и в деталях → «Адреса — главное в заголовке; они не меняются по пути.»
3. **Поля 1** → по одному: `Version: 4`, `Header length: 20 bytes`, `DSCP 0x00`, `Total Length: 52`, `Identification 0x31fc`, `Flags 0x02 (DF)`, `Fragment offset: 0` → по фразе на поле.
4. **Поля 2** → `TTL: 128` (анимация: −1 на каждом маршрутизаторе → 0 → drop), `Protocol: TCP (6)`, `Header checksum`, `Source`, `Destination` → «Protocol говорит, что внутри.»
5. **Пакет 8 (GET)** → та же ветка; подсветка `Total Length: 411`, под IPv4 — TCP и HTTP → «Та же оболочка — в 8 раз больше груза.»
6. **Пакет 16 (ICMP)** → подсветка `Flags: 0x00`, `Protocol: ICMP (1)`, ветка ICMP → «Другой пассажир — другое значение Protocol.»
7. **Карточка** → таблица трёх пакетов: Length на проводе 66/425/74, Total Length 52/411/60, Protocol 6/6/1, Flags DF/DF/0 → итог.

Ассеты: рендер окна анализатора (список, дерево, байты), карточка сравнения, мини-анимация TTL.

**Замечания к оригиналу:** (1) все три «скриншота» — статичные; видео не показывает, как сделать захват — при пересборке либо тоже статично, либо 10-секундная сцена «Capture → Start»; (2) голос: «this packet is not large enough or is not identified for fragmentation» — точнее: бит DF запрещает маршрутизаторам фрагментировать пакет (если он не влезает в MTU — отбрасывается с ICMP-сообщением), размер здесь ни при чём; (3) «header length — minimum size of an IPv4 header» верно (20 байт без Options); (4) в списке пакетов видны «чужие» протоколы (SSDP, Dropbox LAN sync, TCP к 38.112.107.53) — при пересборке лучше чистый захват; (5) Wireshark 1.8.2 (2012) — интерфейс устарел, в новых версиях ветка называется так же, но Total Length и Flags выглядят иначе (`Flags: 0x02, Don't fragment`, `0100 .... = Version: 4`) — отразить в рендере современный вид.
